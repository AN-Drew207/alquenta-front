# Arquitectura — front/ (frontend)

Next.js 16 (App Router) + React 19 + TypeScript strict. shadcn/ui (estilo `base-nova`) sobre Tailwind v4. TanStack Query + axios para datos de servidor, react-hook-form + zod para formularios, next-intl para i18n, next-themes para dark mode, leaflet/react-leaflet para el mapa de búsqueda por ubicación.

Dev: `npm run dev` (puerto 3000).

## Estructura

```
app/            # rutas App Router, route groups: (auth), (app), (app)/(admin), (app)/(superadmin)
components/
  ui/            # primitivas shadcn genéricas, sin lógica de negocio
  properties/, dashboard/, profile/, conversations/, superadmin/, contact/, about/, home/, layout/
hooks/          # hooks de React Query + utilitarios (use-dirty-state, use-reveal, use-require-role)
lib/
  api/          # un archivo por recurso backend (auth.ts, properties.ts, media.ts...) + client.ts (axios) + server-fetch.ts (fetch para RSC)
  i18n/         # labels.ts (cliente) / labels.server.ts (RSC) — labels traducidos de enums, vía build-labels.ts compartido
  data/         # venezuela-locations.ts — datos estáticos estado/municipio
  validations/  # esquemas zod
  env.ts        # única fuente de NEXT_PUBLIC_API_URL / APP_ENV — nada más debe leer process.env directo
types/          # tipos compartidos por dominio (property, auth, admin, plan, messaging, notification, enums)
i18n/request.ts # config next-intl (locale por cookie NEXT_LOCALE, fallback "es")
messages/       # en.json, es.json
```

Convención: `components/ui/` = primitivas shadcn; el resto de `components/` = específico de dominio, alineado 1:1 con secciones de `app/`.

## Routing y protección de rutas

- **No hay `middleware.ts`** (deprecado/renombrado en Next 16). Toda la protección de rutas es **client-side**, vía el hook compartido `hooks/use-require-role.ts` (`useRequireRole(role?)`): sin `role` exige cualquier sesión, con `role` exige ese rol exacto; redirige a `/login?redirect=...` o a `/` y devuelve `{ user, isLoading, isAllowed }`. Usado por `(app)/layout.tsx`, `(app)/(admin)/layout.tsx` (`"ADMIN"`) y `(app)/(superadmin)/layout.tsx` (`"SUPERADMIN"`). `(auth)/layout.tsx` es aparte a propósito — su lógica es la inversa (redirige *fuera* si ya hay sesión) y trae bastante UI propia (logo, panel de imagen), no encaja en el mismo hook.
- Rutas públicas (SSR, Server Components): `app/page.tsx`, `app/properties/[id]/page.tsx`, `app/agencies/[id]/page.tsx`, `about/contact/privacy/terms`, `admin-invite`. `app/robots.ts`/`app/sitemap.ts` (convención nativa de Next 16) generan `/robots.txt` y `/sitemap.xml`, con `lib/env.ts`'s `SITE_URL` para las URLs absolutas — bloquean crawleo de rutas privadas (`/dashboard`, `/my-properties`, `/profile`, etc.).
- Landing pages SEO: `app/[operacion]/[estado]/page.tsx` (ej. `/alquiler/tachira`, `/venta/distrito-capital`) — catálogo pre-filtrado por tipo de operación + estado, con `generateMetadata` propio (`<title>`/`<meta description>` interpolados vía el namespace `landing` de next-intl, usando ICU `select` para conjugar alquiler/venta por idioma — si se agrega una key nueva ahí, el nombre de la variable en el mensaje ICU tiene que calzar exacto con el objeto que se le pasa a `t()`, un mismatch de nombre no tira error, next-intl devuelve la key cruda como texto). Los slugs son deliberadamente en **español y fijos**, independientes del locale activo (`lib/slugs.ts`: `slugify()` para el estado sin tildes, mapeo fijo `alquiler↔RENT`/`venta↔SALE`) — son URLs indexadas y permanentes, no texto de UI. Combos sin ningún listado no tiran 404 (podrían tenerlos mañana), muestran el estado vacío igual que el catálogo; combos con operación o estado inválidos sí tiran `notFound()`. `app/sitemap.ts` solo lista los combos que **sí** tienen al menos un listado activo (evita indexar páginas vacías); `components/home/explore-by-state.tsx` es la otra vía de descubrimiento — una fila de links por estado en la home, visible solo cuando no hay filtros activos (para que `properties` ahí represente el catálogo completo, no uno ya filtrado).
- `(auth)` redirige a la ruta por rol si ya hay sesión; `(app)` exige sesión; `(app)/(admin)` exige `role === "ADMIN"`; `(app)/(superadmin)` exige `role === "SUPERADMIN"`.

## Comunicación con el backend

- `lib/env.ts` → `API_URL` (única fuente de `NEXT_PUBLIC_API_URL`, falla rápido si falta).
- `lib/api/client.ts` → instancia axios (`baseURL: ${API_URL}/api`, `withCredentials: true`, sesión vía cookie httpOnly, sin tokens en localStorage). Interceptor normaliza errores a `ApiError`, `translateApiError()` mapea excepciones de dominio del backend (inglés) a mensajes en español.
- `lib/api/{auth,properties,admins,conversations,media,notifications,plans,profile,profiles}.ts` — un archivo por recurso.
- Server Components (`app/page.tsx`, `app/properties/[id]/page.tsx`, `app/agencies/[id]/page.tsx`, `lib/api/profiles.ts`) no pueden usar el cliente axios (asume contexto browser/interactivo) — usan `lib/api/server-fetch.ts` (`serverFetch(path, fallbackMessage)`), que hace `fetch` con `cache: "no-store"` y reusa `translateApiError()` para que un error en SSR lea el mismo mensaje en español que uno del lado cliente. Devuelve el `Response` crudo así que cada caller sigue decidiendo el caso 404 (`res.status === 404`) por su cuenta.
- Media: no pasa por el backend — `lib/api/media.ts` pide firma (`POST /media/signature`) y sube directo a Cloudinary.
- Reportar propiedad: `components/properties/report-property-dialog.tsx` (visible solo logueado y nunca para el dueño de esa publicación — recibe `adminId` para el chequeo, mismo criterio que `ContactBox`/`FavoriteButton`) + cola en `/superadmin/reports` (`hooks/use-reports.ts`). Motivos son un enum fijo (`ReportReason`), no texto libre — mejor para triage.
- Propiedad `RENTED_OR_SOLD` ("Finalizado", ver `enums.propertyStatus` en los mensajes) es terminal e irreversible en el backend (`api/CLAUDE.md`). El frontend refleja esto en los dos lugares donde el dueño ve acciones sobre su propiedad — `contact-box.tsx` (vista pública) y `my-property-card.tsx` (`/my-properties`) — ocultando Editar/Cancelar y mostrando en su lugar el texto `finalizedNotice`; y en `app/(app)/(admin)/my-properties/[id]/edit/page.tsx`, que redirige a `/my-properties` con un toast si alguien llega ahí igual (link viejo, back button, URL a mano) para una propiedad ya finalizada, en vez de dejar que el wizard cargue y falle recién al enviar.
- Verificación de admin: badge `BadgeCheck` en `/agencies/[id]` y en el panel de SUPERADMIN (`AdminStatusActions` tiene el toggle verify/unverify, sin diálogo de confirmación — a diferencia de disable/delete, es trivialmente reversible). `/agencies/[id]` también muestra tasa/tiempo de respuesta reales (`GET /conversations/admins/:adminId/response-stats`), solo si `sampleSize > 0`.
- WhatsApp del publicador (A-09): `Property` nunca trae el número crudo del backend público — solo `hasWhatsappContact: boolean` y, en la página de detalle (`GET /properties/:id`), `contactRevealToken` (HMAC, 90s de vida). `components/properties/whatsapp-reveal-card.tsx` (client) muestra un botón "Ver WhatsApp"; al click llama `POST /properties/:id/reveal-contact` (`lib/api/properties.ts::revealPropertyContact`, hook `hooks/use-reveal-contact.ts`) con ese token y recién ahí pinta el número + link `wa.me`. Si el token expiró (usuario tardó >90s en hacer click) o el endpoint rate-limitea (10/60s, ver `api/CLAUDE.md`), se muestra un toast vía `translateApiError` — no hay reintento automático, el usuario debe recargar la página para obtener un token nuevo.
- Búsqueda por mapa: `leaflet`/`react-leaflet` (único uso de ambos en el repo). Origen de las coordenadas: el admin marca un pin a mano en `components/properties/location-picker.tsx` (paso "Ubicación y precio" del wizard) — no hay geocoding automático por dirección de texto. El picker se centra en el centroide del estado elegido (`lib/data/venezuela-state-centroids.ts`, datos aproximados solo para centrar el mapa) hasta que se coloca un pin; a partir de ahí cambiar de estado ya no recentra, para no mover un pin ya puesto. Vista pública: `app/page.tsx` tiene un toggle Lista/Mapa (`?view=map`, mismo patrón de query params que el resto de filtros) que renderiza `components/properties/properties-map.tsx` sobre el mismo array ya filtrado — las propiedades sin coordenadas simplemente no aparecen como pin (aviso de cuántas quedan fuera vía `mapUnlocatedNotice`). Ambos componentes de mapa (`location-picker.tsx`, `properties-map.tsx`) tocan `window`/Leaflet en el mount, así que nunca se importan directo desde un Server Component — `location-price-step.tsx` ya es cliente y usa `next/dynamic(..., {ssr:false})` inline; `app/page.tsx` sí es Server Component, por eso pasa por el wrapper cliente `properties-map-client.tsx` (el `ssr:false` de `next/dynamic` no está permitido directo dentro de un Server Component, tiene que vivir detrás de un boundary `"use client"`). El pin usa un ícono SVG propio (`map-marker-icon.ts`, `L.divIcon`) en vez de las imágenes por defecto de Leaflet — evita el problema clásico de rutas relativas rotas bajo bundlers, y toma el color `--primary` del tema. `leaflet/dist/leaflet.css` se importa una sola vez, global, en `app/globals.css`.
- Contacto/mensajería: `components/properties/contact-box.tsx` es la caja lateral de la página de propiedad — su contenido depende de quién mira: dueño → panel de gestión (editar/cancelar/marcar alquilada-vendida); anónimo → CTA de login; CLIENT o ADMIN (no dueño, no SUPERADMIN) → formulario para enviar el primer mensaje, o si `useMyConversations()` ya trae una conversación con ese `propertyId`, una card "Ya enviaste un mensaje" con link a `/conversations/:id` en vez del formulario (así nunca se duplica el primer contacto). Al enviar, redirige a la conversación recién creada. `useMyConversations()` está auto-gateado a `enabled: Boolean(user)` (mismo patrón que `useFavoriteIds`) porque ahora se llama desde una página pública, no solo desde las rutas ya protegidas de `(app)/conversations/*`. Un ADMIN puede contactar a otro ADMIN por su propiedad (nunca la propia — ver nota de `messaging` en `api/CLAUDE.md`); la lista/detalle de conversaciones (`conversation-list.tsx`, `(app)/conversations/[id]/page.tsx`) ya calculaba "el otro participante" por ID (`currentUser.id === conversation.adminId ? clientName : adminName`), así que no necesitó cambios para mostrar bien ambos lados sean CLIENT o ADMIN.
- Favoritos: `hooks/use-favorites.ts` (`useFavoriteIds`/`useFavorites`/mutaciones) + `components/properties/favorite-button.tsx` — no renderiza nada para visitantes anónimos (igual que los íconos de conversaciones/notificaciones en `SiteHeader`). El botón vive como hermano del `<Link>` de la imagen en `PropertyCard`, no anidado adentro, para no meter un `<button>` dentro de un `<a>`.
- `useCurrentUser()` (`hooks/use-current-user.ts`) es la fuente de verdad de sesión (React Query, `staleTime: 5min`, `retry: false`, 401 → `null`). `app/layout.tsx` la prefetchea server-side (`lib/api/auth.server.ts::fetchCurrentUserServer`, reenvía las cookies entrantes a mano vía `next/headers`) y la hidrata con `HydrationBoundary` — así `SiteHeader`/`ContactBox` no muestran un skeleton vacío en el primer paint mientras resuelve la sesión. La query key vive en `lib/api/query-keys.ts` (no en el hook, que es `"use client"`) justo para poder compartirla con el prefetch server-side.

## Componentes

- Mayoría client-heavy (`"use client"` en ~80/121 archivos). Server Components solo en páginas públicas de lectura.
- Formularios: patrón `react-hook-form` + `zodResolver` + `FormProvider` (ver `components/properties/property-wizard.tsx`), hook `use-dirty-state.ts` para "unsaved changes" + `beforeunload`. El wizard exige al menos 1 foto para publicar (mismo mínimo que el backend). El botón "Siguiente"/"Publicar" (o "Guardar cambios" al editar) del footer necesita `key` distintos (`key="next"` / `key="submit"`) en las dos ramas del condicional — sin eso, React reutiliza el mismo nodo `<button>` y solo le muta el atributo `type` de `"button"` a `"submit"` al llegar al último paso, en vez de montar un botón nuevo. Como `goNext()` es async (espera `trigger()` antes de avanzar el step), esa mutación de `type` ocurre después del click pero antes de que el navegador termine de resolverlo, y el resultado es que el propio click que debía solo avanzar al paso de Revisión dispara un submit real — pasaba tanto al crear como al editar. Si se toca este footer de nuevo, mantener los `key` o el bug vuelve.
- `components/properties/property-filters.tsx`: además de los filtros por campo, tiene búsqueda de texto libre (`?search=`, filtra por título en el backend) y un selector de orden (`?sort=newest|price_asc|price_desc|area_desc`, traducido a `sortBy`/`sortOrder` para la API en `app/page.tsx`).
- Labels de enums: `lib/i18n/labels.ts` (cliente, `useTranslations`) y `lib/i18n/labels.server.ts` (RSC, `getTranslations`) comparten un helper (`lib/i18n/build-labels.ts`) y la lista de valores por enum vive una sola vez en `types/enums.ts` (`PROPERTY_TYPE_VALUES`, `OPERATION_TYPE_VALUES` — cada una derivada de un objeto `satisfies Record<Enum, true>` para que TS obligue a listar todos los valores). Si se agrega un valor a un enum, agregarlo también a su objeto `*_KEYS` en `types/enums.ts` — es el único lugar.
- La galería de fotos de propiedades (`components/properties/property-gallery.tsx`) usa `<img>` nativo para las imágenes de Cloudinary, **deliberado**: evita la cuota/costo de optimización de imágenes de Vercel para contenido subido por usuarios (potencialmente mucho volumen). Assets propios del sitio (logo, fotos del panel de auth) sí usan `next/image` vía imports estáticos — la distinción es "Cloudinary vs. local", no inconsistencia accidental.

## Estilos / i18n

- Tailwind v4 vía `@import "tailwindcss"` en `app/globals.css`, sin `tailwind.config.js` (sintaxis `@theme inline`). Variables `--nos-*` para marca (usadas en `app/about`).
- Dark mode: `next-themes`, `attribute="class"`, `defaultTheme="system"`.
- i18n: `next-intl`, sin prefijo de idioma en URL, locale por cookie `NEXT_LOCALE` (`i18n/request.ts`), idiomas `en`/`es`.

## Testing

No hay suite de tests (ni unit ni e2e). CI solo corre `lint` + `tsc --noEmit`. Sin `zustand` ni `playwright` en `package.json` — se sacaron por no tener ningún uso real; si hace falta Playwright para un click-through manual puntual, `npx playwright` lo trae sin necesidad de declararlo como dependencia.
